# 交付与真实渲染验收

## 一、单一内容源

PDF、HTML、可选 Word 和修改说明必须来自同一份 `resume.yaml` 或等价结构化源文件。不要在不同格式里分别手改同一句话；事实变化先改源文件，再重新生成全部交付物。

默认交付：优化版 PDF＋可编辑源文件（YAML，通常附 HTML）＋修改说明。用户要求 Word 时再生成 DOCX，不能用 PDF 或页面截图代替**可编辑** Word。

## 二、真实渲染才算验收

- PDF：检查页数、每页首末内容、文本块越界、照片与 Logo、链接、末页留白。
- Word：用 Word、LibreOffice 或环境可用的真实渲染器打开／导出，再比较全文、重点、分页、照片、分隔线和链接。只看 python-docx 参数不算通过。
- 字体：字体文件已安装或注册表已写入，不等于渲染器已识别；必须检查实际使用字体，避免可变字体默认细字重或静默回退。
- 环境没有 Word 时，交付可编辑源并明确“DOCX 未做真实渲染验收”，不能声称与 PDF 完全一致。

## 三、版式问题修责任源

连续修补仍出现重叠、错位或分页异常时，检查生成方法，不要继续微调边距。旧模板持续破坏几何关系时，按目标版式从零重建比继续填空更可靠。

**不能为排版悄悄删字。** 为保一页或首页完整而压缩文案，必须说明删了什么；优先调整间距、密度和结构，语义变化交给用户确认。

## 四、区分文档失败与 QA 假失败

PDF 可能逐字拆 span，Word 可能合并 bullet 与正文；文本提取顺序也可能不同。比较前统一空白、项目符号和必要的字符规范化。

QA 失败时先判断是文档真的错了，还是比较器不适合。不要为了消除**假失败**去修改正确文档，也不能把真实失败一概归为工具问题。

## 五、修改说明与未决项

交付说明固定包含：

1. 我做了什么：文案、结构、版式、输出文件；
2. 事实依据与标蓝／不标蓝清单；
3. 验收范围和结果；
4. 仍需用户确认的数字、术语、归属与线上显示风险；
5. 需要用户下一步判断的最小问题。

没做浏览器、Word 或线上视觉验收时，明确写“未做”，不把文件生成或 git 推送成功说成视觉验收完成。
